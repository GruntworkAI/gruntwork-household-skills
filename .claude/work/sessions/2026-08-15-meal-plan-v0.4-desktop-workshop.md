# meal-plan Skill Summary (v0.4)

## What this is

A skill that runs a household meal plan as a repeating loop: plan the covered days, acquire the food, cook the meals, and record what actually happened so next week's plan is smarter than this week's. It was workshopped in claude.ai on 2026-08-15, revised through four versions, and tested against a fixture household. This document is the handoff for moving it into a repo via Claude Code.

## Design decisions and why

**Generic by construction.** Nothing household-specific is hardcoded. The family roster, cadence days, dietary goals, acquisition sources, and storage location all live in a per-household config created at first run. This is deliberate: the skill is meant to be shared with other households, and every instruction that would only make sense for one family was pushed into config instead.

**Modes, not days.** The skill has four modes (setup, plan, shop, cook) inferred from what the user says. The cadence (which day is planning day, which days are covered) is config data. One household plans Saturdays for Monday through Wednesday; another can plan Wednesdays for the weekend without touching the skill.

**A consistency dial rather than a variety assumption.** Config carries a 1-to-5 dial. At 5 the plan mode proposes the proven rotation nearly unchanged (defined as the most recent completed week's plan, falling back to highest-rated most-made keepers); at 1 it works the 21-day repeat window hard. The original draft assumed variety was the goal; testing the design against a limited-days household showed consistency is often the point, especially in an early phase.

**Prepared food is first-class.** The meal library carries a prep field (scratch, semi, prepared). A store rotisserie chicken or frozen dumplings are legitimate library rows, proposed on equal footing in plan mode, and shopped as single line items rather than exploded into ingredients. Setup explicitly prompts for prepared staples because users omit them as "not real meals."

**Reality over intention.** The weekly log keeps planned_meal and actual_meal as separate columns, with a status (as-planned, swapped, substituted, bailed). Audibles are honored without friction and recorded without judgment; a bail never auto-creates a library row. Plan-versus-actual is presented neutrally at week's end, as planning data rather than a scorecard.

**Identity at the storage layer.** Multiple contributors (two adults, and eventually a household AI agent with its own credentials) share one state store. The skill authenticates nobody; each contributor reaches the backend with their own credentials, and the backend's sharing model is the access control. The skill's obligations are lighter: ask who's driving, stamp a self-declared `by` column on log rows, re-read state immediately before any write, and never silently delete another contributor's data. An agent contributor is structurally identical to a human one, which is the point.

**Storage-first setup.** Setup provisions and verifies the backend before interviewing (write a sentinel, read it back, never continue on unverified storage), because config has nowhere to live until storage exists, and because an interview whose answers cannot be saved is wasted goodwill.

## State model

Three documents in the configured backend:

1. **config.yaml**: household members (roles adult, kid, agent), goals, cadence, consistency dial, acquisition sources, calendar settings, storage block.
2. **meals.csv**: one row per distinct meal. Columns: name, tags, protein, prep, effort, rating (keep, mixed, retire), times_made, last_made, source, notes.
3. **log.csv**: one row per covered day per week. Columns: week_of, day, planned_meal, actual_meal, status, by, notes.

Backends: github (private repo, documents at root, mode-and-week commit messages), sheet (three tabs mirroring the documents, with a stated degraded paste-back mode if the connector cannot write), local (a directory, for Claude Code use).

## Test status

Four test cases were run against a fixture household (two adults, two kids, ten seeded meals, one completed week of log):

1. First-run setup: interview covers all fields; the prepared-staples prompt earns its place. Pass.
2. Plan at dial 3: correct blended slate, retired meals excluded, project-effort meals excluded from weeknights, mixed ratings flagged with their notes. Pass.
3. Plan at dial 5: exposed an ambiguity ("proven rotation" was undefined). Fixed in v0.4.
4. Pizza audible: executed against a real CSV; planned_meal preserved, status and attribution correct, comma-in-notes quoting handled. Exposed two gaps (a garbled swap instruction, and silence on whether bails enter the library). Both fixed in v0.4.

## Open items for the Claude Code phase

1. Create the repo (private, under a household-controlled account, deliberately not a development org) and land the skill.
2. Decide the household's actual backend and run setup for real; the sentinel write test will settle the sheet-write question empirically if the sheet is chosen.
3. Calendar integration is specified but untested (event-per-dinner with prep notes, shopping block, events updated on audibles). First real week will exercise it.
4. Deferred by design: real authentication, per-person meal ratings, lunches and snacks, expansion beyond three covered days, and any delivery-service ordering integration. Each has a config-level home when wanted; none blocks phase one.
